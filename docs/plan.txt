  Ringkasan

  Ekosistem Melange tidak punya implementasi TEA yang hidup: satu-satunya port, melange-tea, memaku melange = 2.2.0 dan melange-webapi < 3, sedangkan opam sudah di Melange 6.0.1 (OCaml 5.4). Rencana ini membangun penggantinya dengan lingkup sengaja kecil: TEA yang benar, vdom yang bisa diuji tanpa browser, dan efek yang cukup untuk aplikasi nyata.

  Strategi intinya memisahkan dua hal yang selama ini tercampur di melange-tea. Bagian murni — representasi node, algoritma diff, DSL HTML, runtime pesan — ditulis dalam Reason dan tetap berjalan secara native, sehingga bisa diuji dengan dune test tanpa DOM. Hanya lapisan kontak browser yang memakai Melange dan melange.dom, di balik virtual module. Batas itu yang membuat core bisa diuji, dan yang mencegah FFI merembes ke seluruh kode.

  Prinsip yang mengikat

  Lima aturan ini yang membedakan TEA dari sekadar “state management”. Semuanya bisa ditegakkan lewat tipe dan test, dan tidak ada satu pun yang boleh dilanggar demi kenyamanan.

    Satu model per programTidak ada state kedua di luar model — tidak di DOM, tidak di closure, tidak di modul. Kalau sebuah nilai memengaruhi tampilan, ia ada di model.

    update murnimsg -> model -> model, tanpa efek samping, tanpa akses jam/acak/IO. Semua efek keluar sebagai data.

    view murnimodel -> node. Tidak menyentuh DOM, tidak membaca waktu, tidak menyimpan apa pun antar pemanggilan. Karena itu ia bisa diuji sebagai fungsi biasa.

    Efek adalah dataCmd dan Sub menjelaskan pekerjaan; runtime yang menjalankannya dan mengembalikan hasilnya sebagai msg.

    Pesan adalah satu-satunya jalan masukTidak ada mutasi model dari luar loop. Log pesan yang masuk adalah riwayat lengkap aplikasi dan bisa di-replay.

  Keputusan arsitektur

    ADR-01 · Virtual DOM adalah satu-satunya renderer

    view menghasilkan pohon nilai; runtime membandingkannya dengan pohon sebelumnya dan menambal DOM. Hanya ada satu jalur render. Alasannya urutan eksekusi yang bisa diprediksi — satu siklus update → view → patch per frame, berapa pun pesan yang masuk di dalamnya — dan karena view murni, hasilnya bisa diuji sebagai nilai biasa tanpa menyentuh browser.

    ADR-02 · Port bagian murni, tulis ulang lapisan DOM

    Dari melange-tea: vdom.ml (743 baris), tea_app, tea_html, tea_json layak dipertimbangkan karena algoritmanya tidak bergantung compiler. Yang wajib ditulis ulang adalah web_* (±900 baris) yang memanggil melange-webapi.

    ADR-03 · Reason adalah sumber utama

    Seluruh kode perpustakaan, test, dan contoh ditulis sebagai .re / .rei. Dune sudah membawa dialect reason bawaan dan memanggil refmt untuk menghasilkan AST OCaml sebelum melange.ppx berjalan. Konsekuensinya: jangan menambahkan stanza (dialect ...) untuk reason — Dune menolaknya dengan “dialect reason is already defined” — dan .ml di repo hanya boleh berupa artefak di _build.

    ADR-04 · Render di-batch ke animation frame

    Meniru _Browser_makeAnimator di Elm: state NO_REQUEST → PENDING → EXTRA, satu patch per frame, plus satu frame cadangan untuk pesan yang masuk saat draw berjalan. Beberapa pesan dalam satu tick tidak menghasilkan beberapa patch.

    ADR-05 · DSL fungsi, bukan PPX JSX

    Tidak ada .mlx di v0.1. DSL berupa fungsi biasa (Html.div [] [...]) supaya tidak ada lapisan build tambahan, pesan error tetap dari type checker OCaml, dan contoh bisa disalin ke proyek tanpa konfigurasi PPX. Kalau nanti dibutuhkan, JSX bisa jadi paket terpisah tanpa menyentuh core.

    Terverifikasi, bukan asumsi
    Setup di atas sudah dibangun di mesin ini dengan melange 6.0.1-54, dune 3.23.1, dan reason 3.17.3: .re + melange.emit + melange.ppx berhasil menghasilkan JS.   Setelah v0.1: debugger time-travel

  Elm menyertakan debugger di build --debug: setiap msg dicatat, model disimpan per langkah, dan ada panel untuk mundur ke keadaan sebelumnya. Itu sengaja tidak masuk v0.1 — biayanya ada di runtime dan UI panel, bukan di core. Targetnya v0.2 sebagai paket terpisah, tea.debug: bungkus dispatch, simpan log (msg, model), lalu replay dari indeks. Build produksi tidak menyertakan paket itu sama sekali.

  Detail teknis yang menentukan

  Representasi node

  Varian dengan lima kasus: Text, Node (tag, namespace, facts, kids, key), Keyed, Thunk (lazy), dan Tagger (map pesan). Setiap node menyimpan descendants_count, dipakai saat apply untuk melompati subtree yang tidak punya patch — ini yang membuat apply tidak menelusuri DOM nyata secara membabi buta.

  Diff

  Index pre-order, keluaran berupa array patch. Bail-out REDRAW begitu tag atau namespace berubah, jadi struktur yang berubah bentuk tidak di-diff lebih dalam. Keyed diff menangani insert/remove/move dengan reuse node. Thunk membandingkan array argumen secara fisik (==); kalau sama, subtree dilewati sepenuhnya. Fast path x == y sebelum semua itu.

  Kedalaman pohon

  Diff rekursif sedalam pohon adalah satu-satunya tempat kedalaman benar-benar berbahaya. Batas kedalaman 512 dengan fallback iteratif, plus test 5.000 level bersarang, masuk ke P1 sebagai syarat lulus.

  Lapisan DOM

  Tiga hal yang paling sering salah dan karenanya diuji satu per satu: atribut vs properti (value, checked, selected harus properti), style sebagai objek, dan boolean attribute. Listener dipasang per node dan disimpan di properti node itu sendiri supaya bisa dilepas saat patch — tanpa itu, patch berulang meninggalkan handler yatim.

  Runtime

  Satu antrean pesan, update murni, dan Cmd/Sub sebagai bag yang dikirim ke manager. Subscription di-diff: hanya manager yang daftar sub-nya berubah yang di-restart. Render dijadwalkan ke requestAnimationFrame dengan state machine yang sama seperti Elm.

  Anggaran performa

  Angka di bawah adalah target yang harus divalidasi di P0, bukan klaim. Kalau P0 tidak mencapainya dengan margin yang jelas, proyek berhenti sebelum P1.

  Definisi selesai v0.1.0

    Tiga contoh jalan di browser: counter, todo (keyed, 1.000 item), fetch JSON + routing.

    dune test hijau: diff native (properti) dan patch DOM di jsdom.

    Diff cocok dengan implementasi referensi naif pada 10.000 pohon acak.

    Seluruh anggaran performa §9 terpenuhi, hasilnya dicatat di repo.

    Nol dependensi ke melange-webapi; hanya melange.dom dan melange.js.

  Langkah pertama

    Audit lisensi melange-tea. Ini gate pertama: menentukan port atau tulis ulang, dan memengaruhi seluruh isi P1.

    Spike P0: scaffold Dune + Melange 6.0.1, lalu bandingkan tiga jalur pada list 1.000 baris — render ulang penuh, vdom.ml yang di-vendor, dan diff minimal buatan sendiri.

    Kunci kontrak runtime (satu halaman): Program, Cmd, Sub, dan jadwal render. Semua fase berikutnya bergantung pada bentuk ini, dan ia harus selesai sebelum P1 menulis diff.

    Catatan versi: opam saat ini menyediakan melange.6.0.1-54 (OCaml 5.4.x). Upstream sudah merilis 7.x di GitHub, tetapi belum masuk opam-repository, jadi baseline proyek adalah 6.0.1-54 dan matrix CI menambahkan 7.x begitu tersedia.
